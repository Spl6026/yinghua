# 公開快照新鮮度檢查的效能改善（設計提案，待確認）

狀態：**已決定採用方案 D（2026-11-03）**，見文末。方案 A 未實作，沒有新增 migration。

## 1. 現況與量測

公開頁面與公開 API 只讀「最近一次成功發布的快照」。為了保證不提供過期內容，`ContentPublication::read()` 每個請求都會：

1. 讀取並解碼 `current/.snapshot.json`；
2. 用 `PublicationSnapshotBuilder` 從資料庫重新組出「現在應公開的內容」（約 12 個查詢）、整份 JSON 編碼後算 SHA-256；
3. 兩者的 generation 不同就回 503「公開頁面正在更新」，等發布程序重新產生。

同一請求內第二次讀取會沿用已驗證的結果，但每個請求都要做一次完整重建。實測（2026-11-03，本機 Docker）：

| 情境 | 重建與雜湊耗時 | 快照大小 |
| --- | --- | --- |
| 目前資料（景點 7、電影 5、消息 5、優惠 4） | 6.4–8.2 ms | 41 KB |
| 再加 200 筆景點（含一般長度的摘要與介紹） | 33.6 ms | 1.8 MB |
| 再加 800 筆景點 | 98.6 ms | 7.2 MB |

對照：不讀快照的健康檢查約 5.5 ms，目前公開 API 約 18–20 ms。成本隨內容量線性成長，而且由每個公開請求負擔，與流量相乘。開發環境另外每次重新計算前端原始碼的雜湊（約 4.4 ms），但正式映像建置時已預先寫入 `.renderer-version`，正式環境沒有這一項。

## 2. 必須保留的保證

改善不能放寬以下行為。現有測試都依賴這些行為，`publication-alias-order`、`publication-clock` 兩組也剛納入固定套件。

- 內容、舊網址、SEO、一般設定被修改後，下一個請求就不再提供舊快照（不允許「過幾秒才生效」）。
- 沒有人編輯也會自然變化的情況，同樣要立即反映：排程發布時間到、優惠跨日到期、電影換週、程式（renderer）版本改變、正式網址或條款版本設定改變。
- 透過任何途徑寫入都要生效，包括後台 API、CLI 匯入、備份還原，以及直接下 SQL。

## 3. 方案 A（建議）：變更計數＋時間界線，完整比對留作後備

只在「確定沒變」時走快速路徑，有任何疑慮就退回現在的完整比對。完整比對仍是唯一的判準。

1. **變更計數**：新增 migration 022，建立單列資料表 `publication_revision(id, revision)`。在所有組成快照的資料表上建立 AFTER INSERT／UPDATE／DELETE 觸發器，讓 `revision` 加一。觸發器由資料庫執行，可涵蓋 API、CLI、還原與手動 SQL，不必在每個 Repository 補程式，也不會漏掉寫入路徑。
   涵蓋的資料表（由 Builder 實際讀取的查詢整理）：`attractions`、`attraction_aliases`、`films`、`film_aliases`、`film_screenings`、`news_posts`、`news_aliases`、`offers`、`offer_aliases`、`merchants`、`routes`、`route_attractions`、`media_assets`、`content_seo`、`site_settings`。
2. **時間界線**：Builder 組快照時另外記下 `validUntil`，也就是「沒有寫入也可能改變」的最早時間，取以下各項的最小值：
   - 各類內容中，下一筆尚未到的 `publish_at`；
   - 台北時間的下一個午夜（優惠的有效狀態依日計算）；
   - 下一個電影週的開始（本週映演區間）。
3. **快照記錄**：快照多存 `revision`、`validUntil`，以及當時的 renderer 版本、正式網址與條款版本設定。
4. **讀取時的快速路徑**：讀取快照後只查一次 `SELECT revision`（主鍵查詢）。以下全部成立才直接使用快照，否則照舊完整重建比對：
   - revision 相同；
   - 現在時間早於 `validUntil`；
   - renderer 版本、網址與條款設定都相同。
5. **讀取順序**：Builder 要在讀取任何內容「之前」先讀 revision。這樣即使組快照時剛好有人寫入，快照的內容只會比它標記的 revision 新、不會更舊。下一個請求看到 revision 不同，就退回完整比對，不會把過期內容誤判為最新。

預期效果：公開請求的新鮮度檢查從「6–100 ms，且隨內容量成長」降到一次主鍵查詢（約 0.3 ms）。發布程序的 `tick()` 每 10 秒檢查一次，也走同一條快速路徑。

風險與對策：
- **觸發器漏掉某張表**：會讓修改後短暫提供舊內容。對策是測試逐表寫入、確認 revision 增加，並以 Builder 實際查詢的資料表清單對照觸發器清單；新增資料表時測試會失敗提醒。
- **時間界線算錯**：對策是延用並擴充現有的換日／換週／排程測試（`public_content_clock.php`）。
- **觸發器帶來寫入成本**：每次寫入多一個單列 UPDATE。後台寫入量很小，可接受；會員收藏、行程與 session 等高頻表不在清單內。
- **需要回退時**：加一個設定（例如 `PUBLICATION_FAST_CHECK=0`）關閉快速路徑，立即回到現在的行為，不需要回滾 migration。

## 4. 其他方案

- **方案 B：短時間快取**（每個 PHP 程序每 N 秒才完整比對一次）。實作最簡單，但修改後最多 N 秒仍提供舊內容，違反第 2 節的保證，現有測試也會失敗。只有在可以接受短暫延遲時才考慮。
- **方案 C：先不處理**。目前資料量下每個請求約多 6–8 ms，網站內容維持在數十筆時影響不大。可以等內容量或流量接近上表的數百筆時再做。

## 5. 同一路徑上另一個會跟著變大的成本（建議另案）

每個請求都會讀取並解碼整份快照 JSON（800 筆景點時約 7 MB）。公開 API 需要用到快照內容，所以不能省略讀取，但可以改成：

- 依類別拆成多個小檔，只讀需要的部分；或
- 以 generation 為鍵，用 APCu 快取解碼後的陣列。

這會牽動發布檔案格式，建議等方案 A 定案後另行評估，不併入本提案。

## 6. 若採用方案 A 的實作與驗收步驟

1. migration 022：`publication_revision` 資料表與觸發器（新增 DDL，需使用者同意）。
2. Builder：先讀 revision，計算 `validUntil`，寫入快照；`SECTIONS` 增加對應欄位。`PublicationPending` 的診斷沿用 `SECTIONS`，不需要另外維護清單。
3. `ContentPublication::read()`／`ready()` 加上快速路徑，並以設定開關控制。
4. 測試：
   - 逐表寫入後 revision 增加；
   - 觸發器清單與 Builder 讀取的資料表一致；
   - 排程時間到、跨午夜、換週時，即使沒有寫入也要退回完整比對；
   - 組快照途中有並行寫入時，不會誤判為最新；
   - 關閉開關時行為與現在相同；
   - 19 組整合套件與瀏覽器冒煙測試全部通過。
5. 量測：重做第 1 節的三種資料量，記錄改善前後的公開 API 延遲。

## 決定（2026-11-03）：方案 D，信任發布流程

使用者比較一般小型網站的慣例後選擇方案 D：

- `ContentPublication::read()` 直接提供最近一次成功發布的快照，不再每個請求重建比對；只有從未成功發布過時回 503。
- 後台儲存照舊立即重新發布；`tick()`（publisher 每 10 秒）仍做完整比對，負責排程時間到、跨日、換週、直接改資料庫與備份還原後的更新，最多延遲約 10 秒。
- 發布失敗時繼續提供上一版；後台已顯示「已保存，公開同步失敗」並可重試。
- 註冊同意仍要求政策已實際發布（`PublishedPolicies`），加入行程仍即時檢查景點狀態（`MemberAttractions`），這兩項正確性檢查不變。

實測（本機）：公開 API 由約 18–20 ms 降到約 6–8 ms（健康檢查約 5.5 ms）；`read()` 由 6–99 ms（隨內容量）降到固定約 0.5 ms。原本為發布延遲診斷而設的 `SECTIONS` 區段清單與 `projection_changed` 診斷已不再需要，一併移除。
