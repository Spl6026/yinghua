## 發現與修正設計

### R3-01：圖片說明欄位的保存語意需要補查

優先級：高（資料保存正確性）。

已讀程式中，`frontend/assets/js/pages/attraction-form.js` 的景點保存欄位清單不包含 alt／source／license；這三個欄位只在按「上傳圖片」時放入 FormData。然而編輯既有景點時它們仍可編輯。本輪已在隔離後台的原始展示圖片重現：修改三個欄位後按「儲存內容」，畫面回清單；重新開啟編輯頁時，三個欄位全部恢復舊值。此次沒有更動正式環境資料。已上傳資產的同類情境尚待另驗，不把展示圖片結果擴大成所有媒體情境皆已驗證。

修正設計須先區分：景點使用圖片時的說明、共用媒體資產 metadata，以及原始 seed 外部圖片的說明。不可直接修改共用資產，導致其他景點的說明一起被更動。

位置：`frontend/assets/js/pages/attraction-form.js:6`、`:110`；`backend/src/DTO/AttractionInput.php:24` 的輸入白名單也沒有這三個可寫欄位。前次驗收漏掉「不換檔，只修改說明」情境。

採用設計：讓說明隨景點的既有 POST／PUT 一起保存，增加可寫的 imageAlt／imageSource／imageLicense；在 attractions 增對應欄位，空值時沿用原資產資料。表單欄位及讀回 API 使用同一組名稱。上傳後的 media_assets 原始來源／授權紀錄保持獨立，不直接改動共用資產。

新舊內容的替代文字由同一映射提供給後台、公開 API、SSR HTML 及 JS 卡片；發布仍需有效圖片與非空 alt。保存採既有 version／交易／稽核／發布流程，唯讀模擬及欠缺 edit 權限者不能改寫。這是規格圖片／alt 要求的實作補正，具體儲存結構屬 E-18。

驗收：只修改說明、不換檔；替換圖片；同一媒體被多筆引用；唯讀／越權；失敗回滾；重新載入及公開 HTML 的替代文字均有明確結果。

### R3-02：原型列表的順序與文案標籤被改動

優先級：中（使用者指定 U-05）。

已確認兩項差異。`website/js/app.js:6–11` 的原始順序為博物館、東門市場、或者工藝櫥窗、新竹公園、或者咖啡、山房選物所；目前六筆展示資料在公開列表反向排列。`AttractionRepository.php:107` 使用 publish_at DESC／id DESC，受控 seed 同時間發布時會反轉原序。

`website/js/app.js:67` 原先顯示各筆 rating 文案，例如「城市記憶」「巷弄探索」「在地好店」；`frontend/assets/js/pages/attractions.js:7` 及 `frontend/scripts/publish.mjs:22` 統一改為「在地推薦」。原欄位是文案標籤，不能把它當成不存在的星等需求而直接丟掉。這兩項差異未取得使用者指定變更，應依 U-05 補正。

計畫：保留發布時間優先，在相同發布時間採用可重現的次排序，確保原始六筆 seed 為原序。新增 recommendationLabel（文案，不是數值評分），保存原型標籤至 DB／受控 seed，沒有自訂標籤的新內容才使用「在地推薦」。SSR 與 JS 卡片共用同一欄位；不在前端依 legacy_id 硬編另一套原型資料。調整排序時用實際 MariaDB EXPLAIN 評估，不先新增無依據的索引。

其他差異：目前後台清單以更新時間取代原型的營業時間欄；公開詳情新增地址／營業時間／更新日期與收藏按鈕；首頁精選文案改讀 DB。這些逐項列為待對照，區分必要資料串接及非必要顯示改動，不能先宣告全站像素一致。

驗收：桌面及手機都用瀏覽器實際寬度記錄；確認表單、圖片、表格與導覽無水平溢出，並抽查鍵盤焦點、分類切換、空清單與圖片失敗。

### R3-03：失敗／競態測試需擴及新增表單

優先級：中（E-18 品質補充）。

既有 Node 測試包含管理員表單與權限狀態；階段三新增測試主要涵蓋 HTML 產物及返回網址。仍需針對景點表單的載入失敗重試、409 衝突、202 保存但發布失敗、僅 create 權限、新增成功後的狀態切換及上傳期間重複操作建立有意義的行為測試。

計畫：只針對可觀察行為及此次確認的缺口新增測試，不用檢查原始碼字串代替功能驗證；依實際失敗重現決定是否修改共用表單邏輯。

驗收：同時觀察前端提示及真實 API 結果，確定不重複建立資料、不遺失未存輸入，也不在無權限時開放修改。

### R3-04：資料庫座標 CHECK 接受單側 NULL

優先級：低（資料庫完整性；API 已有保護，非已證實的外部越權）。

位置：`backend/database/migrations/002_attractions.sql:52`。條件中的 BETWEEN 在單側為 NULL 時可得到 UNKNOWN，未排除只有 latitude 或 longitude 的資料。本輪於 yinghua_test 交易內將既有測試筆的 latitude 設 NULL、longitude 保留數值，MariaDB 實際接受；交易已回滾。AttractionInput 目前會拒絕這類 API 輸入，兩者不可混為同一層已通過。

計畫：新 migration 先檢查現有單側座標資料，再用明確「兩者皆 NULL，或兩者皆非 NULL 且各在範圍內」的 CHECK 取代舊約束。若發現既有不合法資料先報告，不默默改寫或刪除；不更動已套用的 002 SQL。

驗收：資料庫直接寫入兩個單側 NULL 情境皆拒絕；雙 NULL、合法經緯度可通過；超出範圍拒絕。以隔離交易測試並回滾。
